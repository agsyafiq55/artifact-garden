OAuth 2.0 and OpenID Connect

Every "Log in with Google" button and every app that asks to see your calendar runs on these two standards. OAuth 2.0 lets you give an app limited access to your data without handing over your password. OpenID Connect adds a way for the app to learn who you are. This page walks through one login, message by message, then lets you attack it.

Guess first. You tap "Log in with PhotoCloud" on a printing site, and the site receives an access token. Does that access token prove to the site who you are?

An access token says what the site may do, and it is meant for the API. Proof of who logged in comes from an ID token, which OpenID Connect adds. Part 1 explains the difference.

1Overview of OAuth 2.0 and OpenID Connect

You keep your photos on PhotoCloud. A printing site, PrintShop, wants to print some of them. PrintShop could ask for your PhotoCloud password, but then it could do anything you can do, forever, and you could only stop it by changing your password.

OAuth 2.0 is the standard that fixes this. You let an app act for you with limited rights, and the app never sees your password. The standard names four roles:

  • The resource owner is you, the person who owns the photos.
  • The client is the app that wants access, here PrintShop.
  • The authorization server is the service that logs you in, asks for your approval and issues tokens. Here it is PhotoCloud's login page.
  • The resource server is the API that holds the data, here PhotoCloud's photo API.

When you approve, the authorization server gives PrintShop an access token. This is a string that PrintShop sends to the photo API with each request, in the Authorization header. The token carries a scope, the list of named permissions you approved, such as photos.read, and it expires.

OpenID Connect is a layer on top of OAuth 2.0 that adds identity. When the client asks for the openid scope, the authorization server also returns an ID token. The ID token is a signed JSON Web Token, or JWT, that tells the client who logged in, who issued the token, which app it is for and when it expires.

Think of a hotel. The front desk is the authorization server. It checks your passport once and hands over a key card, the access token, that opens your room and the gym until checkout. The doors read the card, not your name. The registration slip that says who checked in is the ID token. The analogy stops at the guest. In OAuth, the one holding the key card is an app acting for you.

Common mix-up

"OAuth 2.0 logs users in."

OAuth 2.0 only grants access. An access token tells the client nothing reliable about who you are, and it may even be meant for a different app. "Log in with" buttons use OpenID Connect, which adds the ID token for that job.

2How the authorization code flow works

Most apps get their tokens through the authorization code flow. The authorization server first sends back a short-lived, one-time code through your browser. The app then trades that code for tokens in a direct call from its own server. RFC 6749 recommends that a code expire within 10 minutes, and a client may use it only once.

PKCE, short for Proof Key for Code Exchange, ties the code to the app that asked for it. The app makes a random secret, the code verifier, and sends only its SHA-256 hash, the code challenge, at the start. To redeem the code, the app must show the verifier itself. Tap Next to follow one login.

The real messages, step by step

Step 1. PrintShop sends your browser to this address.

GET /authorize?response_type=code
  &client_id=printshop
  &redirect_uri=https%3A%2F%2Fprintshop.example%2Fcallback
  &scope=openid%20photos.read
  &state=af0ifjsldkj
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256 HTTP/1.1
Host: auth.photocloud.example

Step 3. After you approve, the authorization server redirects you back.

HTTP/1.1 302 Found
Location: https://printshop.example/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=af0ifjsldkj

Steps 4 and 5. PrintShop's server redeems the code.

Host: auth.photocloud.example
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fprintshop.example%2Fcallback
&client_id=printshop
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "access_token": "SlAV32hkKG",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "openid photos.read",
  "id_token": "eyJhbGciOiJSUzI1NiIs..."
}

The ID token's middle part decodes to these claims.

{
  "iss": "https://auth.photocloud.example",
  "sub": "user-2481",
  "aud": "printshop",
  "iat": 1795651200,
  "exp": 1795654800
}

Step 6. PrintShop calls the photo API.

GET /v1/photos HTTP/1.1
Host: api.photocloud.example
Authorization: Bearer SlAV32hkKG
  1. The code challenge in step 1 is the SHA-256 hash of the code verifier in step 4. Only PrintShop knows the verifier until step 4.
  2. The state value goes out in step 1 and comes back in step 3. PrintShop rejects a callback whose state it never sent.
  3. The ID token's iss names the issuer, sub names the user, aud names the app it is for, and exp is when it expires.
  4. The access token lasts 3600 seconds, one hour, and covers only openid photos.read.

Which token goes where

TokenWho reads itWhat it says
Authorization codeThe authorization server, onceA one-time ticket to fetch tokens
Access tokenThe resource serverWhat the client may do, and until when
ID tokenThe clientWho logged in, who issued the token and which app it is for

RFC 9700, the current OAuth security advice, says public clients such as mobile and browser apps must use PKCE, and other clients should. It also says clients should not use the older implicit flow, which returned the access token straight in the browser's address.

4Practice questions

Which token does the photo API check, and which one does PrintShop read to learn who you are?

The photo API checks the access token. PrintShop reads the ID token, whose sub claim names you and whose aud claim names PrintShop.

Why does the authorization server send back a code instead of the tokens themselves?

The code passes through your browser, where history, logs and other apps may see it. A code is short-lived, works once and, with PKCE, works only with the verifier. The tokens then travel in a direct call between servers.

A mobile app can't keep a client secret, because anyone can unpack the app and read it. What protects its authorization codes?

PKCE. The app makes a fresh code verifier for every login, so a stolen code is useless without it. RFC 9700 says public clients like this must use PKCE.

Your backend accepts any valid PhotoCloud access token as proof that the user logged in to your app. What's wrong?

An access token is meant for the API, and it may have been issued to a different app. Another app could replay a user's token to log in as them. Your app should check an ID token whose aud claim names your own client ID.

On the HTTP requests and responses page, every request stood alone. Which header carries the access token, and why must every API call include it?

The Authorization header, as Authorization: Bearer SlAV32hkKG. HTTP is stateless, so the photo API remembers nothing from the last call and needs the token on every request.

What to remember

  • OAuth 2.0 grants limited access without sharing a password. OpenID Connect adds identity on top.
  • The access token goes to the API. The ID token stays with the client and says who logged in.
  • Scope limits what an access token can do, even when the token is valid.
  • The authorization code flow sends a one-time code through the browser and the tokens server to server.
  • PKCE ties the code to the app that started the login, so a stolen code can't be redeemed.
