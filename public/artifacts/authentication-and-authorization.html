Authentication and authorization

Authentication checks who sent a request. Authorization decides what that caller may do. Every API with user accounts runs both checks on every request, and each check fails with its own status code.

Guess first. Ana is logged in to a photo app, and her token is valid. Her phone asks for photo 42, which belongs to Ben. What should the API answer?

Her valid token proves who she is, but the photo is Ben's, so the authorization check refuses. Part 2 walks through both checks.

1Overview of authentication and authorization

Snapshelf is a photo app. Ana signs in once with her password, and her phone then sends a token with every request. Ben and Cleo use the same API, and Cleo is an admin who removes photos that break the rules.

Authentication, or authn, checks that the caller is who they claim to be. The caller proves it with a credential: something only they have, such as a password, a session cookie or an access token. If the credential checks out, the server knows the caller's identity, such as the user ana.

Authorization, or authz, decides whether that identity may take this action on this resource. A permission is one allowed action, such as "delete a photo". A policy says who holds it: owners may delete their own photos, and admins may delete any photo.

A safe policy is deny by default. If no rule allows the action, the server refuses it. A new endpoint then stays closed until someone writes a rule that opens it.

At an airport, the passport check proves who you are. That is authentication. Your boarding pass decides which plane you may board. That is authorization. The analogy stops at timing: the airport checks you once, while HTTP is stateless, so an API checks both on every request.

Common mix-up

"The token is valid, so the request is allowed."

A valid token only tells the server who is asking. The server still has to check that this user may touch this object. OWASP ranks the missing check, called broken object level authorization, first on its 2023 list of API risks.

2How an API checks a request

Two refused requests to the photo API

The first request carries no credential. Authentication fails at step 3, and the server names the scheme it accepts in the WWW-Authenticate header, which RFC 9110 requires on every 401.

GET /photos/42 HTTP/1.1
Host: api.snapshelf.example
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="snapshelf"

The second request carries Ben's valid token. Authentication passes, and authorization fails at step 5, because Ben neither owns photo 42 nor holds the admin role.

DELETE /photos/42 HTTP/1.1
Host: api.snapshelf.example
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9...
HTTP/1.1 403 Forbidden

The handler runs the two checks in that order. The can function holds the policy, and its last line is deny by default.

app.delete('/photos/:id', async (req, res) => {
  const user = await authenticate(req);   // step 2
  if (!user) return res.status(401)
    .set('WWW-Authenticate', 'Bearer').end();
  const photo = await db.photos.find(req.params.id);
  if (!photo) return res.status(404).end();
  if (!can(user, 'delete', photo))         // step 4
    return res.status(403).end();
  await db.photos.remove(photo.id);
  res.status(204).end();
});

function can(user, action, photo) {
  if (user.role === 'admin') return true;
  if (photo.ownerId === user.id) return true;
  return false;
}

The name "401 Unauthorized" is old and misleading. A 401 means the server could not authenticate the caller.

4Practice questions

Which check runs first, and what question does each one answer?

Authentication runs first and answers "who is asking?". Authorization runs second and answers "may this caller do this to this resource?". Authorization needs the identity that authentication produced.

Why does a 403 tell the client that logging in again will not help?

The server already accepted the credential and knows who the caller is. The policy refused that identity, so a fresh login brings the same identity and the same answer.

An invoice API verifies the token, then runs SELECT * FROM invoices WHERE id = $1 with the id from the URL. What is missing?

The object level authorization check. Any customer can change the id and read another customer's invoice. Add the owner to the query, such as AND customer_id = $2, or check the owner before returning the row.

Is OAuth 2.0 a login protocol?

No. OAuth 2.0 lets a user grant an app limited access to an API, which is authorization. OpenID Connect adds an ID token on top of it, and the ID token tells the app who logged in, which is authentication.

An access token carries the scope photos:delete. Can Ben now delete Ana's photo?

Not by itself. The scope limits what the app may do on Ben's behalf. The API still checks its own policy for photo 42, and that policy says only the owner or an admin may delete it.

What to remember

  • Authentication finds out who is asking. Authorization decides what they may do.
  • A failed authentication returns 401. A failed authorization returns 403, or 404 to hide the resource.
  • A valid token is no permission. Check every object the request reads or changes.
  • Deny by default. If no rule allows the action, refuse it.
