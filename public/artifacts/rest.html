REST

REST is the style behind most web APIs you will call or build. It says an API is a set of resources, each with its own URL, that every client reads and changes with the same few HTTP methods. This page explains the style, walks one request through it, then lets you drive a REST API.

Guess first. An API has the endpoint POST /deleteOrder?id=7. It works, and it returns JSON. Is it REST?

In REST, the path names a thing, such as /orders/7, and the method names the action, such as DELETE. Part 1 explains why that split matters.

1Overview of REST

A food app needs to list orders, show one order, place a new one, change it and cancel it. One way is to invent an endpoint for each job: /getOrders, /createOrder, /cancelOrder. Every new job then needs a new endpoint, and every client must learn each one.

REST, short for Representational State Transfer, takes another approach. Roy Fielding described it in his 2000 dissertation as a set of constraints for building systems like the web. Its core ideas are these:

  • A resource is any thing the API exposes, such as one order or the list of all orders. Each resource has its own URL, such as /orders/7.
  • A client never touches the resource itself. It gets a representation of it, such as a JSON document of the order's current state, and sends representations back to change it.
  • A uniform interface means every resource is used through the same small set of methods with fixed meanings: GET reads, POST creates, PUT replaces, PATCH changes part, DELETE removes. A client that knows these methods can use any resource.
  • Each request is self-contained, as HTTP's statelessness already requires. The server keeps no memory of the client between requests.
  • Representations carry links to related resources and next actions. This is called hypermedia. A client follows the links instead of building URLs by hand, as a browser follows links on a web page.
Think of a library. Every book has a shelf mark, which is its URL. The desk offers the same few actions for every book: look it up, borrow it, return it. You never get the book's master record, only a copy of it on paper, which is the representation. The analogy stops at the actions. A library invents new services over time, but a REST API keeps the same methods and adds new resources instead.

Common mix-up

"Any API that sends JSON over HTTP is a REST API."

REST is a set of constraints, and JSON isn't one of them. MDN notes that people often call any HTTP API "REST" loosely. An API with verbs in its paths, such as /deleteOrder, uses HTTP without the uniform interface.

2How a REST API handles a request

Creating an order, line by line

To add to a collection, the client sends POST to the collection's URL.

POST /orders HTTP/1.1
Host: api.restaurant.example
Content-Type: application/json

{"dish": "Roti canai", "qty": 1}
HTTP/1.1 201 Created
Location: /orders/9
Content-Type: application/json

{"id": 9, "dish": "Roti canai", "qty": 1,
 "links": {"self": "/orders/9", "collection": "/orders"}}
  1. The path is a plural noun, /orders. The method, POST, says what to do with it.
  2. The server picks the new order's URL and returns it in the Location header with 201 Created.
  3. The body is a representation of the new resource, with links the client can follow next.

The uniform interface on a collection and an item

Method/orders, the collection/orders/7, one item
GETList the ordersRead order 7
POSTCreate a new order405, not allowed
PUT405, not allowedReplace order 7 with the body
PATCH405, not allowedChange some fields of order 7
DELETE405, not allowedRemove order 7

RFC 5789 explains the PUT and PATCH split. PUT replaces the whole resource, so a field missing from the body is gone. PATCH applies only the changes in the body. When a resource doesn't support a method, the server answers 405 Method Not Allowed with an Allow header that lists the methods it does support.

Fielding's full list of constraints also covers caching and layers, such as proxies between client and server. Leonard Richardson's maturity model, which Martin Fowler explains, ranks APIs by how far they go: resources first, then HTTP methods and status codes used as HTTP intends, then hypermedia links.

4Practice questions

In a REST API, what does the URL name, and what does the method name?

The URL names a resource, such as /orders/7. The method names the action, such as GET to read it or DELETE to remove it.

Why does a uniform interface make a new resource cheap to add?

Clients, caches and tools already know what GET, POST, PUT, PATCH and DELETE mean. A new resource such as /invoices works with all of them at once, without a new verb to learn.

You're adding payments. Which requests would create a payment for order 7 and then read it?

POST to a collection such as /orders/7/payments to create it. The 201 response's Location header names the new resource, such as /orders/7/payments/1, and GET on that URL reads it.

A client wants to change only the quantity of order 7. A teammate sends PUT with just {"qty": 3}. What goes wrong?

PUT replaces the whole resource, so every field missing from the body, such as the dish and the note, may be wiped. PATCH changes only the fields in the body.

On the HTTP requests and responses page, GET was a safe method. Which REST operations on an order may a crawler send without changing anything?

Only GET and HEAD, such as GET /orders/7. POST, PUT, PATCH and DELETE all change the resource, so they never belong behind a plain link.

What to remember

  • A REST API is a set of resources, each with its own URL named by a noun.
  • Clients get and send representations, such as JSON, never the resource itself.
  • The uniform interface gives every resource the same methods: GET reads, POST creates, PUT replaces, PATCH changes part, DELETE removes.
  • A server answers an unsupported method with 405 and an Allow header.
  • Hypermedia links in each representation tell the client where it can go next.
