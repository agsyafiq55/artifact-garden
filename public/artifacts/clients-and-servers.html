Clients and servers

Almost every app you use is split into two programs. One runs on your device and asks for things. The other runs somewhere else and answers. This page explains how the two talk, then lets you run the conversation yourself.

1The idea

A client is a program that asks for something. A server is a program that waits for those requests, does the work, and sends back an answer. The browser on your laptop and the app on your phone are clients. The computer that stores your orders, messages or photos runs a server.

Client

  • Starts every conversation.
  • Shows results to a person.
  • Keeps little or no shared data.
  • Many clients run at the same time.

Server

  • Waits for requests and answers each one.
  • Holds the shared data and the rules.
  • Serves many clients at once.
  • Runs on a machine you never see.

Client and server are roles, not kinds of machine. The same program can be a server to your phone and, a moment later, a client of another service.

Think of a restaurant. You are the client and the kitchen is the server. You place an order, the kitchen cooks only when an order arrives, and the food comes back to your table. The kitchen keeps the stock. Your table doesn't.

2One request, step by step

  1. The client sends a request. It names a method, which says what to do, such as GET to read or POST to create. It also names a path, which says what to do it to, such as /menu.
  2. The server does the work. It checks the request, reads or changes its data, and may ask other services for help.
  3. The server sends one response. The response carries a status code that says how it went, and usually a body with the data.
  4. The client uses the response. It shows the menu, confirms the order, or shows an error.

What they look like

This is a real HTTP request that places an order, and the server's reply.

POST /orders HTTP/1.1
Host: api.restaurant.example
Content-Type: application/json

{"dish": "Laksa"}
HTTP/1.1 201 Created
Content-Type: application/json

{"id": 1, "dish": "Laksa", "status": "received"}

Reading a status code

2xxIt worked. 200 OK returns data, and 201 Created confirms something new was stored.
4xxThe client asked for something wrong. 400 Bad Request or 404 Not Found. The server is fine.
5xxThe server failed while doing the work, as in 500 Internal Server Error.
NoneNo response arrived before the client gave up. This is a timeout, and the client can't tell whether the server did the work.

4Check yourself

What to remember

  • The client always starts the conversation. A server only answers.
  • Each request gets one response, and its status code says how it went.
  • The server holds the shared data, so every client sees the same orders.
  • Client and server are roles. A server becomes a client when it calls another service.
Your phone shows the order you placed on your laptop. Where does that order live?

On the server. Neither client stores it. The phone asked the server for the list, and the server sent back every order it holds.

A request comes back with 404. Whose mistake is it?

Usually the client's. A 4xx code means the request asked for something the server can't find or won't accept. A 5xx code means the server itself failed.

Can a server send a request?

Yes. When the restaurant server asks a payment service to charge a card, it is the client in that conversation.

An order request timed out. Did the server get the order?

The client can't tell. The request may have been lost on the way, or the server may have stored the order and the response got lost. Retrying safely needs care, which the idempotency topic covers later on the roadmap.
