HTTP requests and responses

Every time an app talks to a server over the web, it sends an HTTP request and gets an HTTP response. Both are short pieces of text with a fixed layout. This page takes one apart line by line, then lets you build your own and see how a server answers.

Guess first. An app sends a valid JSON order to a strict server, but it leaves out the Content-Type header. What happens?

A strict server may reply 415 Unsupported Media Type. Without Content-Type, it can't tell that the bytes in the body are JSON. Part 2 shows how a server reads a request.

1Overview of an HTTP message

You tap Place order in a food app. The app writes a few lines of plain text and sends them to the restaurant's server. The server reads them, stores the order and writes a few lines back. Those lines of text are HTTP.

Each piece of text is an HTTP message. The app's message is a request, and the server's message is a response. Every message has the same four parts, in this order:

  • A start line. In a request, it is the request line, with the method, the target path and the HTTP version. In a response, it is the status line, with the version, the status code and a short reason phrase such as Created.
  • Headers, one per line. Each header is a name, a colon and a value, such as Host: api.restaurant.example. A header states one fact about the message.
  • A blank line. It tells the reader that the headers have ended.
  • An optional body that holds the data itself, such as the order written as JSON.

One header matters for every body. The Content-Type header names the format of the body, such as application/json. Without it, the server can't tell whether the bytes are JSON, form data or plain text.

Think of a parcel. The start line is the instruction on the front, the headers are the labels, the blank line is the tape, and the body is what's inside. The label "contains glass" tells the courier how to handle the contents, as Content-Type tells the server how to read the body. The analogy stops at the reply. A parcel gets no answer, but every HTTP request gets exactly one response.

Common mix-up

"I set Content-Type to application/json on my GET, so the server will send JSON back."

Content-Type describes the body of the message it sits in. To ask for a format back, the client sends the Accept header, such as Accept: application/json.

A real exchange, line by line

The phone asks for order 2. This request has no body, so it ends at the blank line after its last header.

GET /orders/2 HTTP/1.1
Host: api.restaurant.example
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 26

{"id": 2, "dish": "Laksa"}
  1. The request line names the method GET, the target /orders/2 and the version HTTP/1.1.
  2. Accept asks for JSON back. The response's Content-Type confirms that the body is JSON.
  3. Content-Length tells the phone to read 26 bytes of body.
  4. 200 is the status code, and OK is the reason phrase. Programs check the code. The phrase is for people reading logs.

The layout of every HTTP/1.1 message

<start line>
<header name>: <value>
<header name>: <value>

<optional body>

Methods that only read

A safe method asks the server only to read. GET, HEAD and OPTIONS are safe, so browsers, caches and crawlers send them freely. A server may still write a log line, but the client asked for no change. Of the methods below, only POST, PUT and PATCH requests carry a body.

Every request stands alone

HTTP is a stateless protocol. The server keeps no memory of earlier requests from the same client, so each request carries everything the server needs. A logged-in app sends a Cookie or Authorization header with every request for this reason. The server reads that header to look up who is asking.

4Practice questions

What tells a server that the headers have ended?

A blank line. Everything before it is the start line and headers, and everything after it is body. The server then reads as many bytes as Content-Length says.

Why does a server need Content-Type when it can see the body?

The body is only bytes. The same bytes could be JSON, form data or plain text, and each needs a different parser. Content-Type tells the server which parser to use.

A crawler follows every link on your site, and one link is GET /orders/7/delete. What goes wrong?

The crawler deletes order 7. Crawlers and caches treat GET as safe and send it freely. An action that changes data belongs on DELETE or POST.

Your client wants JSON back from a GET. Should it set Content-Type: application/json?

No. A GET has no body, so Content-Type has nothing to describe. The client sends Accept: application/json to ask for JSON in the response.

On the clients and servers page, the server answered both the phone and the browser. HTTP is stateless, so how does it know who is logged in on each request?

Each request carries the answer itself, in a Cookie or Authorization header. The server reads that header on every request, because it remembers nothing from the last one.

What to remember

  • Every HTTP message has a start line, headers, a blank line and an optional body.
  • A request starts with the method, target and version. A response starts with the version, status code and reason phrase.
  • Content-Type describes the body in the same message. Accept asks for a format back.
  • GET, HEAD and OPTIONS are safe. They ask the server only to read.
  • HTTP is stateless, so every request carries what the server needs, such as a Cookie header.
