Tokens and JWT

After you log in, an app needs a way to prove it's you on every later request. Servers hand the app a token for that job, and the most common format is the JSON Web Token, or JWT. This page shows what a token is, takes a JWT apart, then lets you try to forge one.

Guess first. You paste a JWT into a decoder, and you don't have the server's key. Can you read the user ID inside it?

The payload of a JWT is only encoded, so anyone can decode and read it. The key is needed to make or check the signature, not to read the claims. Part 1 explains why.

1Overview of tokens and JWTs

You log in to a shop app once, then browse your orders for an hour. HTTP is stateless, so the API remembers nothing between requests. After the login, the server gives the app a token, and the app sends it in the Authorization header of every request.

Tokens come in two kinds:

  • An opaque token is a random string with no meaning of its own. The server keeps a table from token to user and looks the token up on every request.
  • A JSON Web Token, or JWT, carries the facts itself. RFC 7519 suggests you say it like the word "jot".

A JWT is three parts joined by dots: a header, a payload and a signature. The payload holds claims, which are named facts about the user and the token, such as sub for the user ID and exp for the expiry time. The signature is computed from the header and payload with a key that only the server knows. If anyone changes one character of the header or payload, the signature no longer matches.

The header and payload are written in base64url, an encoding that turns any bytes into letters, digits, - and _, so the token fits safely in a URL or a header. Encoding is not encryption. Anyone can turn base64url back into the original text.

Think of a festival. An opaque token is a cloakroom ticket: a number that means nothing until staff look it up. A JWT is a wristband printed with your name and "VIP until Sunday", sealed with a hologram that only the organiser can make. Each gate reads the band and checks the hologram without calling the office. The analogy stops at the hologram. Anyone can recognise a hologram, but checking an HS256 signature needs the same secret key that made it.

Common mix-up

"A JWT is encrypted, so I can put an email address or a password in it."

A normal JWT is signed, not encrypted. The signature stops anyone changing the claims, but anyone holding the token can read them. jwt.io warns against putting secrets in the payload.

  1. The signature is the base64url of HMAC-SHA256 over the first two parts and the dot between them, keyed with the server's secret.
  2. iat and exp are seconds since 1 January 1970. Here exp is 3600 seconds after iat, so the token lasts one hour.
  3. role is a claim the shop made up. RFC 7519 lets apps add their own claims next to the registered ones.

The parts of every JWT

base64url(header) . base64url(payload) . base64url(signature)

RFC 7519 registers these claim names. Each one is optional, and an app decides which it needs.

ClaimMeans
issWho issued the token
subWho the token is about, such as a user ID
audWho the token is for. An API rejects a token whose aud doesn't name it.
expWhen the token stops being valid
iatWhen the token was issued
jtiA unique ID for this token

HS256 uses one shared secret to sign and to check, so every API that checks tokens could also make them. RS256 and ES256 sign with a private key and check with a public key, so an API can check tokens without being able to make them.

That last row is why access tokens that are JWTs expire fast, often within an hour. The app also gets a refresh token, a long-lived token that it sends only to the login server's token endpoint to get a fresh access token. The login server checks the refresh token against its own records, so a banned user stops getting new access tokens.

3Try to forge an admin token

You hold the user token from part 2. The endpoint GET /admin/reports only answers tokens whose role claim is admin. Change the token, then send it and watch the API's checks.

  1. Predict, then check. Change the role claim to admin, keep the original signature, and predict the status code before you tap Send.
  2. Re-sign the edited token with a guessed key, then try removing the signature with alg none.
  3. Send the untouched user token two hours after login.
  4. Re-sign with the server's key, and think about what that means for where the key lives.

4Practice questions

What are the three parts of a JWT, and what separates them?

The header, the payload and the signature, each base64url-encoded and joined by dots. The header names the algorithm, the payload holds the claims, and the signature covers both.

Why can't a user change their role claim from user to admin?

The signature was computed over the original header and payload with the server's secret. A changed payload gives a different HMAC, and the user can't compute the right one without the key, so the API rejects the token.

You ban a user at 10:00, but their JWT access token expires at 10:45. What happens at 10:15, and what can you do?

The API still accepts the token, because it checks only the signature and exp. Keep access tokens short-lived, refuse the user's next refresh token, or keep a denylist of jti values until those tokens expire.

A teammate wants to put the user's email and phone number in the JWT payload. Is that private?

No. Anyone who holds the token can decode the payload, because base64url is an encoding. Put in only what the API needs, and keep personal data on the server.

On the OAuth page, PrintShop checked the ID token's aud claim. Why should an API check aud before it trusts a JWT?

A token issued for one app could be replayed against another app that trusts the same issuer. Checking that aud names this API rejects tokens meant for someone else. RFC 8725 lists this as a known attack.

What to remember

  • A JWT is a base64url header, payload and signature joined by dots.
  • Anyone can read the claims. The signature only stops changes.
  • An API checks the algorithm, the signature, then exp, iss and aud, before it trusts any claim.
  • An opaque token needs a lookup but can be revoked at once. A JWT needs no lookup but stays valid until exp.
  • Short-lived access tokens plus a refresh token keep a stolen or revoked JWT from lasting long.
